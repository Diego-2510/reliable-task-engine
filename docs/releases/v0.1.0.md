# Reliable Task Engine v0.1.0

**Proposed publication text: this local candidate is not yet tagged or published.
The release description below applies after the reviewed `v0.1.0` tag exists.**

## Summary and supported environment

This is the first tagged release of a synthetic, trusted-local engineering MVP.

Reliable Task Engine demonstrates durable job processing and transactional outbox
handling with Python 3.12 (`>=3.12,<3.13`), FastAPI, SQLAlchemy 2, psycopg 3,
Alembic and PostgreSQL 16. Dependencies are pinned in `uv.lock`; validation used
uv 0.12.17 on Linux with Docker and Compose. Other Python/PostgreSQL major versions
and operating systems are not verified by this evidence.

## Core components and reliability

- FastAPI submission/status API with optional durable submission idempotency.
- Independent workers using PostgreSQL `SKIP LOCKED`, database-time leases,
  ownership fencing, bounded attempts and delayed recovery.
- Atomic job success and opt-in outbox intent in one transaction.
- Dispatcher with separate claim, synthetic receiver and acknowledgement commits;
  stable event IDs, receiver deduplication, bounded delivery and dead letters.
- Explicit local replay that adds budget while preserving IDs and historical attempts.

There is **no exactly-once execution or delivery guarantee**. Fencing protects
PostgreSQL transitions, not arbitrary external effects. A final-attempt dead letter
may already have a receiver effect; an unknown COMMIT result may already have
committed. Progress requires database availability, continued polling and budget.

## Observability

Manual OpenTelemetry spans, process-local counters and duration histograms are
available in opt-in console mode; default telemetry is disabled. JSON logging
uses fixed allowlisted fields. No collector or network exporter is required.
Read-only diagnostics queries aggregate durable state. Telemetry is best-effort,
resets on restart and is not an authoritative database ledger.

## Fault injection and test evidence

Phase 4A records 350 passing PostgreSQL tests, zero skipped, including real worker
SIGKILL, fresh-process recovery, concurrent claims/submissions, lock-wait expiry,
stale writers, real transaction aborts, uncertain commit responses and dispatcher
crash after receiver commit before acknowledgement. Final-attempt ambiguity and
stable-ID replay are covered. Phase 4B reruns the full suite and clean candidate
smoke; see the linked validation record for exact current results and warnings.
The historical audit retains its original execution context.

## Reproducible benchmark evidence

| Saved baseline | Result |
| --- | ---: |
| Job-only, one worker | 46.90 jobs/s |
| Job-only, eight workers | 316.81 jobs/s |
| Eight-worker speedup / scaling efficiency | 6.76× / 84.4% |
| One dispatcher, across 1/2/4/8 workers | 39.94–42.20 acknowledgements/s |

Two profiles, three measured repetitions of 1,000 jobs per configuration,
separate warm-ups and 36,000 latency samples support these numbers. Handlers are
essentially no-op, effects are rows on the same PostgreSQL instance, and HTTP
submission is bypassed. These are synthetic backlog-drain rates, not real-network
or production measurements and not measured HTTP end-to-end latency. Saved CSVs
regenerate the reports. The dirty-run provenance remains disclosed; source
fingerprint equivalence is not a clean-run claim. No full matrix was rerun for
this license/documentation candidate.

## Installation and security

**Trusted local use with synthetic data only.** No authentication or tenancy is
provided. Do not expose the API/database publicly or use development passwords
for a public service. There is no production-facing deployment recommendation.

After publication, on a fresh checkout with Docker/Compose, free loopback ports
5432/8000 and no existing project volume to preserve:

```sh
git clone --branch v0.1.0 https://github.com/Diego-2510/reliable-task-engine.git
cd reliable-task-engine
docker compose up --build --scale worker=2
```

Compose migrates the new database before starting the API, workers and dispatcher.
For Python development, install uv 0.12.17 and run `uv sync --locked`; follow the
README for explicit database configuration and process startup. Stop all existing
application processes before upgrading an intended existing installation. Never
point destructive tests or benchmark preparation at a development database.

## Important limitations

No real downstream HTTP, automatic retention, key/deduplication expiry, heartbeat,
cancellation, graceful worker drain, bounded database I/O timeout or automatic
restart policy. No fairness, ordering, completion deadline or eventual success
is guaranteed. The image runs as root; resource limits and production security
controls are outside this MVP. Deleting identity rows removes replay protection.
